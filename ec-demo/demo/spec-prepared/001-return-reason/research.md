# Research: 返品理由 (Return Reason) の追加

**Feature**: `001-return-reason` | **Date**: 2026-11-17 | **Plan**: [plan.md](./plan.md)

> ⚠️ **PO確認待ち**: spec.md の NEEDS CLARIFICATION 3件は、ユーザー指示により **暫定で A を採用** して設計を進めている。
> ただし「理由は記録のみ・返金ルールは変えない」という指示 (および FR-006 / BR-10) と矛盾する部分は採用していない (R-02 参照)。
> PO の回答で結論が変わった場合は本ファイルと plan.md を更新する。`docs/business-rules.md` は本機能では変更しない。

## R-01: 理由によって返金ルールを変えるか (spec US3 / FR-010)

- **Decision (暫定 A / PO確認待ち)**: 今回は **理由の記録のみ**。返金額・返金可否・返品期限は理由に依存させない。`refund-calc.js` / `refund-service.js` は変更しない
- **Rationale**: `docs/business-rules.md` に理由別ルールが存在せず、FR-010 は「PO が決定・承認し ID を付与したルールのみ」を許可している。US3 は P3 で、P1/P2 とは独立にリリースできる
- **Alternatives considered**:
  - B (今回の範囲に含める): 理由ごとの返金額・返送料負担・期限を PO が決める必要があり、現時点では推測実装になる → 却下 (constitution 原則1)
  - C (不良品のみ例外): 同上。BR-10 の変更を伴う可能性があり人間承認が必要 → 却下
- **US3 の扱い**: 本 plan のスコープ外。PO が BR-xx を採番・承認した後に別 feature として spec → plan を起こす

## R-02: 返品理由「不良品」と商品状態「不良品 (defective)」の関係 (spec US2 シナリオ3 / FR-007)

- **Decision (暫定 / PO確認待ち・要ユーザー確認)**: **返金可否の判定は従来どおり商品状態 (condition) のみで行う**。理由と状態の食い違いは受け付けて、そのまま記録する。
  - 実質的には選択肢 **B と同じ挙動** になる
- **Rationale**:
  - 選択肢 A (「理由が不良品なら状態も不良品とみなす」) を文字どおり実装すると、**理由「不良品」・状態「開封済」の申請が返金可能に変わる**。これは BR-10 (人間決定) の判定結果を変え、FR-006 と今回の指示「返金ルールは変えない」に反する
  - CLAUDE.md「人間決定のルールと矛盾する実装は直さず報告する」に従い、A の適用はせず、矛盾として報告する
  - 状態のみで判定する現行ロジックを維持すれば、どの選択肢が最終決定されても後から差分を足すだけで済む (A なら判定前に condition を上書き、C ならバリデーションを1つ追加)
- **Alternatives considered**:
  - A をそのまま適用: BR-10 の結果が変わる → 却下 (人間承認が必要)
  - C (食い違いをエラー): 現在受け付けている申請 (例: 理由「サイズ違い」・状態「不良品」) を新たに拒否することになり、返金可否の実質的な変更 → PO 決定前は却下
- **テストへの影響**: US2 シナリオ1・2 は現行 BR-10 どおりなのでテスト化する。シナリオ3 は **期待値未定のためテストを書かない** (tasks では「PO回答待ち」でブロック)

## R-03: 返品理由の単位 (spec Edge Cases / FR-008)

- **Decision (暫定 A / PO確認待ち)**: **返品申請ごとに1つ**。理由の違う商品は別の申請に分ける
- **Rationale**: 既存の部分返品 (BR-11) は複数回の申請を許可しているため、理由ごとに申請を分ける運用が可能。データ構造は `Return.reason` の1フィールドで済み、`ret.lines` の形 (= `calcRefundAmount` の入力) を変えずに済む → FR-006 / SC-003 のリスクが最小
- **Alternatives considered**:
  - B (明細ごと): `lines[].reason` が必要。返金計算の入力に余計なフィールドが混ざる。後から B に移行する場合は「申請の理由を全明細にコピー」で移行可能
  - C (申請ごと + 明細で上書き): 最も複雑。PO 決定前に作る理由がない

## R-04: FR-001 (理由必須) と既存テストの両立 — **要ユーザー/人間確認**

- **問題**: 既存テスト (`test/returns.test.js`, `test/refunds.test.js`) と `test/helpers.js` は `requestReturn(order, items)` を **理由なしで** 呼んでいる。FR-001 をそのまま `requestReturn` に適用するとこれらが失敗する。CLAUDE.md により既存テストは編集できない
- **Decision (提案)**: 理由必須の **新しい入口 `submitReturn(order, items, { reason, comment })`** を追加し、購入者の申請経路 (`src/cli.js` 等) はこちらを使う。既存の `requestReturn(order, items)` は挙動を変えず、`reason: null` (= 未設定) を記録する「旧経路」として残す
  - 両者は内部で同じ検証・記録処理を共有し、BR-09〜BR-11 の判定は1か所のまま
- **Rationale**: 既存テスト・ゴールデンテストを一切変えずに FR-001〜FR-005 を新入口で満たせる。FR-009 (理由なしデータの処理継続) も自然に満たす
- **Trade-off / リスク**: `requestReturn` を使えば理由なしの新規申請が作れてしまう。これは FR-001 の「新規申請は理由必須」を API レベルでは完全には強制しない
- **Alternatives considered**:
  - `requestReturn` に第3引数を追加し必須化 → 既存テストが落ちる。テスト修正は人間承認が必要
  - `createReturnService({ clock, requireReason })` で切り替え → デフォルト値の選び方次第で同じ問題が残り、設定ミスで必須化が外れる
- **確認したいこと**: (1) 上記提案で進めてよいか、(2) それとも既存テストを `reason` 付きに更新することを人間が承認するか

## R-05: 理由・コメントの値と検証 (実装詳細 — BR-15 の範囲)

- **Decision**:
  - 理由コード: `'defective'` (不良品) / `'wrong_size'` (サイズ違い) / `'not_as_expected'` (イメージ違い) / `'other'` (その他)。表示名は日本語の固定ラベルとして同じモジュールで定義
  - 旧データ (未設定) は `reason: null`。集計時は「未設定」として数える (SC-005)
  - コメント: 任意。`undefined` / 空文字は受け付け、記録は `null` に正規化しない (空文字はそのまま `''`、未指定は `null`)。文字数は **コードポイント数** (`[...comment].length`) で数え、500 超は拒否。文字列以外は拒否
  - エラーコード: `REASON_REQUIRED` / `INVALID_REASON` / `COMMENT_TOO_LONG` / `INVALID_COMMENT`
- **Rationale**: エラーコード名・内部値は BR-15 により実装詳細。日本語の UTF-16 長ではなくコードポイントで数えると、絵文字等でも「500文字」の直感と一致する
- **Alternatives considered**: 表示名 (日本語) をそのまま値に使う → 表記ゆれ・比較ミスのリスク。理由「不良品」のコードを condition と同じ `'defective'` にすると混同しやすいが、別フィールド (`reason` vs `lines[].condition`) なので許容。混同防止はテストで担保する

## R-06: 検証順序と「拒否時に状態を変えない」(FR-005 / SC-002)

- **Decision**: 既存のチェック順 (状態 → 期限 → 空 → 明細) の **後、`order.returns.push` の前** に理由・コメントを検証する。全検証を通過するまで `order` を一切変更しない (現行構造を維持)
- **Rationale**: 既存のエラー優先順位 (例: 期限切れ時は `RETURN_WINDOW_EXPIRED`) を変えない。在庫・返金は返品申請時点では触らないため、`order` 不変で FR-005 を満たす
- **Alternatives considered**: 理由を最初に検証 → 既存エラーとの優先順位が変わり、既存テストと同じ入力でも別のエラーになりうる

## R-07: 技術選択 (確認のみ)

- Node.js 20 / ESM / 依存なし / `node --test`: 既存リポジトリと constitution 原則5 に従う。新規依存なし
- 時刻: `requestedAt` は既存どおり `clock()` から取得。`Date.now()` / `new Date()` は使わない
- 金額: 本機能は金額を扱わない。返金計算コードに変更なし
