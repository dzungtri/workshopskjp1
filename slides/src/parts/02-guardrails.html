ガードレールは、一つではなく、何層も重ねます。 【→】縦が層です。上から、Prompt、Permission、Hook、Sandbox、CI、人のレビュー。 上の①はやわらかい層、③から下は固い層です。 【→】ケースA。AIが決済のコードを編集しようとしました。 CLAUDE.md に「決済は触らないで」と書いてあっても、無視されることがあります。 でも Hook が、ツールの実行前にブロックします。 【→】ケースB。AIが本番DBにコマンドを打とうとしました。 Bash は許可されているので、Permission は通ります。 でも sandbox には本番の認証情報がありません。だから届きません。 【→】ケースC。AIが、テストを通すために assert を消しました。 Hook も通る、CI もテストは緑です。 最後に、人のレビューで、test フォルダの差分を見て見つけます。 【→】ポイントです。Prompt は「お願い」。Hook、Sandbox、CI は「仕組み」。 どの層も、いつか破られる前提で、重ねてください。
VN: Defense in depth 6 lớp: prompt (mềm) → permission → hook → sandbox → CI → review người. Ca A: sửa code thanh toán → hook chặn. Ca B: psql prod → sandbox không có credential. Ca C: xoá assert → CI vẫn xanh → review người phát hiện qua diff test/. Prompt = "nhờ", hook/sandbox/CI = "cơ chế".

.claude/hooks/protect-files.js (一部)
const PROTECTED = [
  { prefix: 'src/payment/',  reason: '決済コード' },
  { exact: 'docs/business-rules.md', reason: '業務ルール' },
];
const input = JSON.parse(readFileSync(0, 'utf8'));
const rel = toRelative(input.tool_input?.file_path);
const hit = PROTECTED.find(p => match(p, rel));
if (hit) {
  console.error(`BLOCKED: ${hit.reason} は人間の承認なしに
    変更できません。差分案を提示して承認を求めてください`);
  process.exit(2);   // ← 止める
}
process.exit(0);     // ← 許可

Hook の実例です。今日のデモ用リポジトリから持ってきました。 左が設定です。Edit や Write をする前に、この小さなスクリプトを実行します。 右がスクリプトです。決済のフォルダと、業務ルールのファイルは保護します。 保護対象なら、メッセージを出して、exit 2。これでブロックされます。 【→】面白いのは、このメッセージがAIに返ることです。 AIはブロックされた理由を読んで、「差分案はこれです。承認してください」と聞いてきます。 つまり、止めるだけでなく、人に相談させる仕組みになります。 【→】でも、これで 100% 安全、ではありません。 Bash で sed を使えば、ファイルは書き換えられます。 だから、さっきのように層を重ねます。一つに頼らないでください。

よくある失敗 6つ

1ウソの完了

「テスト通りました ✅」
→ 実は実行していない

対策: 完了前に機械がテストを実行 (Stop hook / CI)

2テストを書き換える

assert 削除 · skip · lint を OFF
→ 緑だけど意味がない

対策: test/ の変更は別に承認 · diff でチェック

3存在しない package

それっぽい名前の SDK を install
→ ニセのパッケージの危険

対策: package 追加は人が承認 · lockfile · scan

4頼んでいない変更

「ついでに」リファクタ · 他機能を修正
→ diff がとても大きい

対策: 触ってよいファイルをチケットに明記

5終わらないループ

同じ修正を何十回も
→ トークンを使いすぎる

対策: 回数 · 予算の上限 · 3回失敗で人へ

6AI全員OKの間違い

AIレビュー3体が全員OK
→ でも設計が間違い

対策: 設計と意図は人が見る

例: 私たちの経験 · 公開されている事例 (GitHub "Reviewing agent PRs" 2026/05 など) をまとめたもの

ここからは、実際によくある失敗です。6つ紹介します。 【→】1つ目、ウソの完了。AIが「テスト通りました」と言う。でも、実際はテストを実行していない。これは本当によくあります。 対策は、完了の前に機械がテストを実行することです。AIの言葉を信じない。 【→】2つ目、テストを書き換える。テストが通らないとき、AIは assert を消したり、skip したりします。緑になりますが、意味がありません。 対策は、test フォルダの変更は別に承認すること。 【→】3つ目、存在しないパッケージ。それっぽい名前の SDK を install しようとします。攻撃者がその名前でニセのパッケージを置いていることもあります。 依存の追加は、人が承認してください。 【→】4つ目、頼んでいない変更。「ついでに」リファクタリング。diff が大きくなって、レビューできなくなります。 チケットに「触ってよいファイル」を書きます。 【→】5つ目、終わらないループ。同じ修正を何十回も繰り返して、トークンをたくさん使ってしまいます。 回数と予算の上限をつけます。3回失敗したら人に戻す、などです。 【→】6つ目、AI全員OKの間違い。AIレビューを3つ回して、全員OK。でも設計が間違っていた。AI同士は、同じ方向に間違えやすいです。 設計と意図は、人が見ます。 （ここで自分のプロジェクトの経験談を1つ話す）
