METR という研究機関の実験です。2025年に行われました。 経験のある OSS 開発者 16人が、自分のリポジトリで、246個の本物のタスクをやりました。 AIを使うタスクと、使わないタスクを、ランダムに分けています。 【→】始める前の予想は「24%速くなる」。 【→】終わった後の感覚も「20%速くなった」。 【→】でも、実際に測ると……19%遅くなっていました。 理由は、プロンプトを書く時間、待つ時間、そして AI が書いたコードをレビューする時間です。 ただし、注意してください。 人数は少ないですし、2025年前半のモデルです。「AIは役に立たない」という話ではありません。 大事なのは、感覚だけでは分からない。測らないと分からない、ということです。
VN: METR RCT: dự đoán +24%, cảm nhận +20%, đo thật −19%. Nguyên nhân: prompt, chờ, review output. Cảnh báo trung thực: mẫu nhỏ, model cũ → thông điệp "phải đo".

今日の地図です。この式を覚えてください。 Agent は、Model に、いくつかの部品を足したものです。 【→】Model は、私たちが買うものです。毎月、勝手に良くなります。私たちは変えられません。 【→】Context。モデルに何を見せるか。これは E のパートです。 【→】Tools。モデルが何をできるか。A で見ます。 【→】Guardrails。何をさせないか。B のパートです。 【→】Feedback。テストやレビューで、結果をチェックする仕組み。C と D です。 【→】Model 以外の部分を「Harness（ハーネス）」と呼びます。 もともとは、馬につける道具のことです。馬が強くても、道具がないと、仕事はできません。 このハーネスを作るのが、私たちエンジニアの仕事です。
VN: Công thức Agent = Model + Context + Tools + Guardrails + Feedback. Model mua, không đổi được; phần còn lại = harness (yên cương ngựa) = việc của kỹ sư. Map từng phần vào khối A–E.

今日は、一つの例をずっと使います。よくある EC サイトです。 商品、カート、在庫、クーポン、注文、決済、返品、返金。 皆さん、毎日使っていますよね。説明はいりません。 【→】でも、ルールは誰が決めるでしょうか。 1回の注文で、同じ商品を何個まで買えるか。 在庫が何個以下になったら、発注するか。 返品は何日以内か。クーポンを使った注文の返金はいくらか。 消費税の端数は、注文ごとか、商品ごとか。 【→】AI に「EC サイトを作って」と言うと、AI はこれをそれっぽく、勝手に決めます。 しかも、ちゃんと動きます。だから気づきにくい。 この問題は、今日のすべてのパートに出てきます。 ※ 例はすべて架空です。
