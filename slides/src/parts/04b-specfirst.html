昔からある V-Model で見てみます。 【→】一番下がコード。今は、ここが AI のいちばん速い所です。 【→】左上が要件、spec.md です。User Story、FR、受入シナリオ。 右上が、それを確かめる受入テストです。Given、When、Then。 FR-001 には、FR-001 のテスト。左と右がつながっています。 【→】設計の plan.md には、結合テスト。 【→】タスクには、単体テスト。golden test や境界値です。 【→】ポイントは3つです。 1つ目。テストは、Spec を書くときに作ります。コードを見て作ると、コードをなぞるだけのテストになります。 2つ目。AIの時代は、真ん中のコードはほぼタダです。価値は両側、Spec と確認に移ります。 3つ目。昔の V と違って、機能ごとに小さな V を何回も回します。ウォーターフォールではありません。
VN: V-Model: đáy = code (AI nhanh nhất). Trái: spec.md ↔ acceptance (Given/When/Then), plan.md ↔ integration, tasks ↔ unit (golden/biên). FR-001 ↔ test FR-001 (truy vết). 3 ý: test viết khi viết spec (tránh test "copy code"); thời AI code gần như miễn phí → giá trị ở 2 cánh; nhiều V nhỏ theo từng feature, không phải waterfall.

これを実際にやる道具です。GitHub の Spec Kit を使います。 【→】specify で、何を作るか、なぜ作るかを書きます。clarify では、AIが質問してきて、人が答えます。 【→】plan で作り方、tasks で1タスク1PRに分けて、analyze で spec と plan と tasks のズレをチェックします。 【→】implement では、テストを先に書きます。 【→】管理は GitHub です。tasks.md のタスクを、GitHub MCP で Issue にします。PR は「Closes #12」で Issue につなげます。最後に人がレビューして、マージ。 【→】こうすると、FR-001、Issue、テストの名前、PR が、全部つながって見えます。 では、実際にやってみます。
VN: Spec Kit: specify → clarify (NGƯỜI trả lời) → plan → tasks → analyze → implement (test trước). Quản lý bằng GitHub: tasks.md → Issue qua GitHub MCP → PR "Closes #12" → người review/merge. Truy vết: FR ↔ Issue ↔ tên test ↔ PR. Chuyển sang DEMO ④.
