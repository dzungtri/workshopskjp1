「ループエンジニアリング」についてのご質問もありました。 ループ自体はシンプルです。計画して、実行して、確認して、直す。これを繰り返します。 大事なのは、どうやって止まるかを設計することです。 【→】成功の止まり方。受入条件のコマンドが、全部 exit 0。 【→】失敗の止まり方。同じ失敗が3回続いたら、止めて人に戻す。 【→】予算の止まり方。回数、時間、トークンの上限。 【→】そして、相談の止まり方。未決定のルール、権限の外、設計の判断。ここは質問して待ちます。 止まり方が決まっていないループは、ずっと回り続けるか、ウソをついて止まります。
VN: Loop engineering = thiết kế cách DỪNG: thành công (mọi lệnh tiêu chí exit 0), thất bại (3 lần cùng lỗi → trả người), ngân sách (số lần/thời gian/token), hỏi (TBD, ngoài quyền, quyết định thiết kế). Không có điều kiện dừng → chạy mãi hoặc báo xong giả.

⏱ 56:30–59:00 (2.5分) · → 4回
ループのやり方で、最近有名なのが「Ralph Loop（ラルフ・ループ）」です。 コードはこれだけ。シェルの while ループで、同じプロンプトを何度も渡します。 【→】ポイントは、毎回新しいセッションで始めることです。コンテキストは毎回まっさら。だから汚れません。 【→】では、記憶はどこにあるか。ファイルと gitです。 計画のファイル、進捗のファイル、そして git log。 【→】プロンプトの中身はシンプルです。計画から1つだけ選んで、実装して、テストして、学んだことを書いて、コミット。 【→】良い点は、コンテキストが汚れないので、長い時間回せることです。 悪い点は、計画とテストが弱いと、同じ間違いを何度も繰り返すことです。 つまり、Ralph Loop も、良いチケットと良いテストが前提です。 ちなみに、Claude Code の公式プラグインは、同じセッションの中で回す方式なので、少し違います。
VN: Ralph loop: while; cat PROMPT.md | claude -p; mỗi vòng context sạch; bộ nhớ nằm ở file (fix_plan, progress) + git. Ưu: không bẩn context, chạy lâu. Nhược: plan/test yếu → lặp lại cùng lỗi. Plugin chính thức chạy trong cùng session (khác bản gốc).

⏱ 61:30–63:30 (2分) · → 6回


マルチエージェントについてです。
分けるなら、「役割」で分けるのがおすすめです。

【→】実装するエージェント。
【→】テストを書くエージェント。仕様だけを見て書きます。実装を見ないのがポイントです。
【→】レビューするエージェント。新しいコンテキストで、diff だけを見ます。実装した時の思い込みがありません。
【→】それから subagent。調査は別のコンテキストでやって、要約だけを返します。これはパートEで詳しく話します。

【→】でも、使わない方がいい時もあります。
同じファイルを同時に触る時。設計の判断がバラバラになる時。全部の会話を共有して、コンテキストが汚れる時。
そして、ハーネスがまだ弱い時です。

【→】私のおすすめは、まず1つのエージェントと、良いハーネス。並列はその後です。


VN: Multi-agent chia theo vai: implement / test (viết từ spec, không xem code) / review (context mới, chỉ xem diff); subagent cho điều tra → trả tóm tắt. Không nên khi: cùng sửa 1 file, quyết định thiết kế lệch nhau, chia sẻ toàn bộ hội thoại (ô nhiễm context), harness còn yếu. Trước tiên: 1 agent + harness tốt.
